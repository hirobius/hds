## Principle

HDS feels lively (ADR-064). Every motion must look effective and intentional: it shows
where something came from, what changed, or that an action worked.

- **Open and close:** things grow from where they came from, and close faster than they open.
- **Arrive:** a confirmation can land with a small spring overshoot.
- **Swap:** a value that changes in place cross-fades with a slight blur.
- **Reduced motion:** every recipe has a still version. Things appear and disappear, nothing moves.

## Recipes

Use a recipe instead of writing a timing. Spread it on a `motion` element:

```tsx
import { AnimatePresence, motion } from 'motion/react';
import { useMotionRecipe } from '@hirobius/design-system';

function Menu({ open }: { open: boolean }) {
  const recipe = useMotionRecipe('openMenu');
  return <AnimatePresence>{open && <motion.div {...recipe}>…</motion.div>}</AnimatePresence>;
}
```

| `listItem`    | List items entering, leaving and moving                       |

## Springs

Springs come in two families, from Material 3's motion system: **spatial** for things that
move (`spatialFast`, `spatialDefault`, `spatialSlow`) and **effects** for fades, colour and
blur (`effectsFast`, `effectsDefault`, `effectsSlow`), which never overshoot. `elastic` is
the lively one, for arrivals. In CSS each spring is a `linear()` curve
(`--primitive-easing-spatialDefault`); in JS it is `hds.motion.springs.spatialDefault`.

## Best practices

- Use a recipe; don't write durations, curves or offsets by hand.
- Close faster than you open.
- Save the overshoot for moments that confirm something; everyday controls settle without it.
- Press feedback is colour and contrast, not a scale change.
- Don't animate things the user did not act on, and don't loop.
