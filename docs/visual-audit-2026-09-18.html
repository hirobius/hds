Every finding below was measured in a real browser — computed styles and WCAG ratios from rendered DOM, not read off source. Findings are split into two tracks because they pull in opposite directions: Drift is code disagreeing with the spec, and the fix is to move the code. Direction is the spec encoding rules you no longer want, and the fix is to move the spec first — fixing drift toward a rule you intend to drop is wasted work.

Two P0s were fixed in place because the audit could not otherwise run: Storybook did not build, and when it did it rendered in the wrong typeface. Everything measured here was captured after those two fixes, on a correctly-rendering Storybook.

Track A · Drift — code disagrees with the spec

Mechanical. No decisions needed; the spec already says what these should be.

P0A1

Storybook preview does not build on a clean clone

What is happening
src/app/data/component-api.json is gitignored (.gitignore:99) and untracked. Only prebuild:lib generates it — build-storybook had no pre-step, so Rollup fails: Could not resolve "../data/component-api.json". The preview bundle is never emitted; only the manager shell is.
Why it matters
Storybook is the only visual surface (#161 retired the Playwright suites; #90 deleted the docs SPA). It has not built on main. Chromatic (#200) could not have produced a baseline even with the token set.
Also
pnpm build-storybook still exits 0 — the inner ELIFECYCLE … exit code 1 is swallowed by the telemetry prompt. CI would report this green.
Which gate should have caught it
No gate builds Storybook. check:full never invokes it.
Fix
Added prebuild-storybook + prestorybook → node scripts/generate-component-api.mjs. Applied.
P0A2

Storybook rendered the whole system in a fallback typeface

What is happening
src/styles/fonts.css declares @font-face with absolute URLs (/fonts/satoshi/satoshi-500.woff2). .storybook/main.ts declared no staticDirs, so every font request 404s.
Why it matters
Verified in-browser: document.fonts.check("500 17px Satoshi") returned false before the fix, true after. Every visual review anyone has done in Storybook was of the wrong face — and a Chromatic baseline would have frozen that in.
Which gate should have caught it
None. No validator resolves a font URL against what the dev/build server actually serves.
Fix
Added staticDirs: ['../public']. Applied.
P0A3

Radio renders no visible control at all

What is happening
The indicator ring and its inner dot are both display: inline. width does not apply to non-replaced inline elements, so the ring computes width: 8px but lays out at 0px.
Why it matters
A selected radio is invisible — only the label renders. The styling is all correct underneath: the ring carries rgb(30,46,253) accent and the dot #fff at radius: 9999px. It is purely a layout-mode bug.
Evidence
Which gate should have caught it
check-layout-discipline, check-dimensions and the 112 stories all pass — none renders and measures.
Fix
Give both spans an explicit box display (inline-flex). src/app/components/radio.tsx:24,38.
P0A4

Segmented control items are white-on-white

What is happening
Item text computes rgb(255,255,255) over rgba(0,0,0,0) on a white page. Measured contrast 1.00:1.
Why it matters
Same root pattern as A3 — a component reaches for content.onAccent (white) without the accent surface behind it. The control is legible only by accident of hover.
Evidence
Which gate should have caught it
check-contrast.mjs checks declared token pairs, not rendered foreground-over-actual-background.
Fix
Bind item colour to the resting surface; reserve onAccent for the selected item once its accent background paints.
P1A5

Three sibling controls, three different outcomes

What is happening
Measured in-browser: Checkbox — 20×20, display:flex, accent background. Correct. Radio — 0px wide (A3). Toggle — a 16×16 transparent box, not a switch track.
Why it matters
These three ship as a set and a consumer will place them in one form. Only one of them is right.
Which gate should have caught it
None compares peer components against each other.
Fix
Bring radio and toggle onto the checkbox's box model.
P1A6

Form-control borders fail WCAG 1.4.11

What is happening
--semantic-color-border-default: #E5E5E5 on white = 1.26:1. Non-text UI affordances require 3:1.
Why it matters
The border is the only affordance on input, textarea, select, combobox and secondary button — there is no fill to carry it. Everything else measured passes comfortably (body 18.88:1, primary button 7.33:1, error 6.47:1, success 5.48:1, warning 7.09:1).
Which gate should have caught it
check-contrast.mjs covers text pairs only.
Fix
A direction call, not a mechanical one — see B3. The minimum compliant neutral against white is roughly #949494, which is a visibly heavier line than you have now.
P1A7

DESIGN.md contradicts its own generated tables

What is happening
Hand-authored prose in DESIGN.source.md:44 says interactive controls use “a restrained 4px radius via the action radius token”. The generated table directly beneath says 12px. Separately the typography prose says headings are 500 and body 400; the generated ramp says 700 and 500.
Why it matters
This is the first file a prospective client or contributor reads, and it disagrees with itself inside one screen.
Which gate should have caught it
build-design-md.mjs regenerates the auto blocks but never diffs the hand-written prose against them.
Fix
Correct the prose, then add a validator that fails when a number in prose contradicts the generated block beside it.
P2A8

The type scale inverts at the top

What is happening
primitive.typography.size.5xl = 80px, 7xl = 72px. The larger name is the smaller value.
Why it matters
Both are published in public/hds-manifest.json and src/app/data/foundations/typography.json, so the docs surface a scale that runs backwards.
Which gate should have caught it
check-token-structure.mjs validates shape, not ordering.
Fix
Renumber, and add a monotonicity assertion to the token-structure check.
P2A9

weight.light (300) is orphaned

What is happening
Its own description reads “Swiss-canon heading weight. Display and h1/h2 composites only.” Those composites all use weight.bold (700).
Why it matters
Someone began moving the headings to a lighter register and it never landed. Worth knowing before you re-decide — see B4.
Which gate should have caught it
check-ghost-tokens / audit-tokens --full did not flag it.
Fix
Either adopt it (B4) or delete it. Leaving it is the worst of the three.

Track B · Direction — the spec itself is the question

You said some of the visual rules are no longer ones you align with. These are the six places where the system states an intent, and changing it is a decision rather than a fix. Each one names the call that is yours to make.

B1

Radius — four numbers for one concept

Where it stands
Surface Rendered Source
Button, Input, Select, Combobox, Textarea, Tab 10px rounded-md = calc(var(--role-radius) - 2px)
Segmented item, Card, Toggle label 12px rounded-[var(--semantic-radius-action)]
Segmented container 16px calc(var(--semantic-radius-action) + 4px)
Surface 8px primitive.radius.8
Badge, Alert 4px —
DESIGN.md prose 4px hand-authored
Diagnosis
Two parallel radius systems. Tailwind derives from --role-radius with a -2px offset (the shadcn convention); HDS components bind --semantic-radius-action directly. Same intent, different number, in components that sit side by side. A Card at 12px containing a Button at 10px also breaks nested-radius geometry — an inner corner should be the outer corner minus its inset, not one pixel tighter.
The call that is yours
Pick one source of truth and one value. The minimal-technical register you described runs tighter than where you are — a single action radius in the 6–8px band, containers one step above it, and the Tailwind -2px derivation deleted so rounded-md cannot disagree with the token.
B2

The type ramp is largely not applied

Where it stands

Declared scale: 10 · 13 · 15 · 17 · 20 · 24 · 30 · 36 · 48 · 72 · 80. Measured in rendered components:

Rendered Where On scale?
11px Badge no
14px Card body copy no
16px Card root, Alert, Segmented, Radio, Toggle no — browser default
18px Card heading (h3 token = 20px) no
Diagnosis
Components that set no font-size inherit the browser's 16px default, which is not a token value. Four off-scale sizes are rendering today. This is the largest single contributor to the system not reading as one system.
The call that is yours
This one is not a taste call — the ramp should be applied. But which ramp is a taste call, so decide B3 first and apply once.
B3

Body weight and the border weight — the two that set the register

Where it stands
Token Now Effect
body 17px / 500 Large and medium-weight. Reads editorial and soft.
ui 15px / 500 Buttons match; inputs render 400, so labels and fields disagree.
border.default #E5E5E5 — 1.26:1 Below the 3:1 floor (A6). Reads as an absent edge.
Diagnosis
You named Vercel and Linear as the target. The thing that actually separates that register from yours is not radius or colour — it is that body copy sits smaller and lighter, and the hairline that bounds a control is visible. A 500-weight 17px body over a 1.26:1 border is the specific combination producing “soft” rather than “precise”.
The call that is yours
Two numbers to choose: body size/weight, and the border neutral. Dropping body to 400 and darkening the border to clear 3:1 are the highest-leverage edits in this entire audit, and they touch two token values.
B4

Heading weight — a move you already started

Where it stands
All of display · h1 · h2 · h3 are 700. weight.light (300) exists, unused, described as the “Swiss-canon heading weight” for exactly those composites.
Diagnosis
Someone set out to take the headings light and stopped. The prose in DESIGN.md still claims headings are 500 (A7) — a third position. Three different intents are recorded in the repo right now.
The call that is yours
Resolve to one. A lighter heading at large sizes is the more restrained register and it is already tokenised; 700 at 72px is the loudest thing in the system.
B5

One accent doing two jobs

Where it stands
semantic.accent.rest and semantic.color.feedback.info are both #1E2EFD.
Diagnosis
An informational alert is chromatically identical to a brand call-to-action. DESIGN.md states feedback hues are “never decorative” — but the info hue is the decorative accent.
The call that is yours
Either give info its own neutral-leaning treatment, or drop the info variant and let neutral carry it. Most restrained systems do the latter.
B6

Card has an invisible border

Where it stands
Rendered card: background #FAFAFA, border-width 1px, border-color rgba(0,0,0,0), radius 12px.
Diagnosis
DESIGN.md defines elevation.flat as surface.page + border.subtle 1px. What ships is a light grey block with a transparent border — the 1px is reserving layout space and painting nothing.
The call that is yours
Decide whether a resting card is bounded by a visible hairline or by a fill. Your own rule — depth is border or shadow, never both — is good; it just is not implemented.

Order of work

  1. Land the two applied fixes (A1, A2) so Storybook builds and renders truthfully. Without this nothing else is reviewable.
  2. Decide B3 — body size/weight and the border neutral. Two token values, and they set the register everything else is judged against.
  3. Then B1 and B4 — radius source of truth, heading weight. Both are single-value decisions once B3 fixes the register.
  4. Then apply the ramp (B2) and fix A3–A6 in the same pass, since the components being touched overlap.
  5. Then A7–A9 — docs and token hygiene, once the values have stopped moving.
  6. Gate each decision as it lands: a monotonicity assertion on the scale, a rendered-contrast check for non-text affordances, a prose-vs-generated-table diff. Register each in docs/guardrails/registry.json.

On the 1:1 against Vercel and Linear

This session's sandbox blocks outbound web access, so those two systems could not be measured here and no numbers for them appear in this document. scripts/measure-reference.mjs ships with this audit: it takes any URL and prints the same computed-geometry table used throughout — control height, radius, padding, border colour and contrast, type size and weight. Run it against the reference systems from a machine with network access and the comparison becomes measured rather than remembered.

The honest version of the comparison is B3. The distance between this system and that register is mostly body weight and a visible hairline — not radius, and not colour.
